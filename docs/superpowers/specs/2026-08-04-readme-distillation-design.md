# FHIR Care Copilot README Distillation Design

Date: 2026-08-04
Status: approved
Working branch: `codex/readme-distill`
Baseline: `v0.2.1` at `46b85339b71191f9e9459944d2dd1afad18a45a9`

## 1. Objective

Turn the current evidence-heavy README into a recruiter-first project front page. It should let an
AI/backend hiring reviewer understand the system, its strongest security decision, its evidence,
and how to run it in about two minutes, while directing deeper review to a small set of canonical
documents.

This is documentation-only work. It does not add a product feature, change runtime behavior, alter
the UI, weaken the synthetic/non-clinical boundary, or claim clinical readiness.

## 2. Editorial target

- Reduce the README from 242 lines to approximately 140–170 lines; 180 lines is the hard ceiling.
- Keep no more than eight top-level sections and avoid nested sections unless needed for clarity.
- Use short paragraphs, one compact security table, one compact evidence summary, and one quick-start
  block.
- Remove repeated explanations, per-test links, per-report links, ADR links, long metric tables,
  fault-injection detail, performance detail, and portfolio self-commentary from the README.
- Preserve deeper evidence in its existing committed artifacts rather than duplicating it.

## 3. Information architecture

The rewritten README will use this order:

1. Title, existing status badges, one-sentence positioning, and an immediate synthetic/non-clinical
   disclosure.
2. Three primary review links: live demo, the existing 75-second demo video, and case study. The
   latest release remains available through the existing release badge.
3. `為什麼值得看`: three bullets covering server-injected patient scope, verifiable FHIR
   references, and PII-safe/reproducible operations.
4. One existing product screenshot, embedded without a standalone screenshot section or an
   explanation of how it was captured.
5. `架構`: one vertical Mermaid diagram plus a short explanation of the request/evidence flow.
6. `安全邊界`: a compact table separating verified protections from explicit non-goals.
7. `證據與限制`: a short, traceable validation summary and links to the model card, data card, and
   security policy.
8. `快速開始` followed by a compact technology/data/license closeout.

## 4. Link and media budget

- Retain only links that materially help a reviewer decide whether to inspect or run the project.
- Allow at most seven prose/documentation links: live demo, demo video, case study, model card,
  data card, security policy, and license. Badge targets are excluded from this count.
- Do not link individual tests, evaluations, reports, workflows, ADRs, scripts, or screenshots from
  the README.
- Keep exactly one existing screenshot: `docs/screenshots/02-answer-with-evidence.png`.
- Do not use a `截圖` heading and do not emphasize that screenshots are generated by a script.

## 5. Vertical Mermaid design

Use `flowchart TB` so GitHub renders a readable top-to-bottom architecture on desktop and mobile.
Limit the main path to concise nodes:

`React UI → FastAPI → Agent/orchestrator → read-only tool registry → FHIRStore → Synthea bundles`

Two side branches show the provider adapter and audit/telemetry path without widening the primary
flow. Node labels will be short, and high-contrast Mermaid classes will explicitly set both fill
and text color. The supporting sentence must preserve these truths:

- patient scope is injected by the server before tool execution;
- the model receives schema-shaped tool output and evidence, not direct database access;
- the local Synthea bundle store is the demo default, while HAPI FHIR remains an optional stub, not
  a claimed production integration.

## 6. Claims and terminology guardrails

- Use `API key` consistently; the Chinese term currently used for it will not remain in the README.
- State that API-key authentication is optional demo/service authentication, not patient-level
  authorization or tenant isolation.
- State that patient-scope enforcement prevents model-controlled patient selection, but does not
  by itself authenticate or authorize a caller.
- Describe FHIR references as verifiable resource references, not sentence-level grounding.
- Describe all included patient resources as Synthea synthetic data and the application as a
  non-clinical portfolio demonstration.
- Do not turn passing tests, evaluations, Docker smoke, CodeQL, or dependency scans into claims of
  production or clinical readiness.
- Prefer stable evidence summaries; exact counts appear only when verified from the current tree.

## 7. Verification

Acceptance requires:

- README length is at most 180 lines.
- Mermaid uses `flowchart TB`, has concise labels, and renders without syntax errors.
- README contains exactly one local screenshot and no standalone screenshot-generation section.
- No Chinese API-key term remains; all user-facing occurrences use `API key`.
- Prose/documentation links remain within the seven-link budget and all local targets exist.
- Synthetic-data, non-clinical-use, authentication/authorization, patient-scope, HAPI-stub, and
  reference-integrity boundaries remain explicit.
- Focused public-claim/release checks and the full CPU-safe backend and frontend suites pass.
- The final diff changes README/documentation only, preserves a clean tree after commit, and uses
  only `kuotunyu <61350295+kuotunyu@users.noreply.github.com>` as author and committer.

## 8. Out of scope

- Runtime, API, agent, FHIR-store, authentication, CI, Docker, dependency, or UI changes.
- New screenshots, evaluations, features, model calls, deployment changes, tags, or releases.
- Real medical data, paid APIs, GPU execution, or clinical/diagnostic/treatment claims.
- Commit-history rewriting, co-author trailers, or any contributor identity other than `kuotunyu`.
