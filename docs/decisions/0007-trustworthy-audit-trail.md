# ADR 0007：可信任的稽核軌跡是一個命題，不是三個功能

- 狀態：Accepted
- 日期：2026-07-25
- 相關：[ADR 0001](0001-scope.md)（唯一寫入路徑）、[ADR 0004](0004-ops-controls-from-domain.md)、營運層 Phase 4

## 背景

`POST /api/care-notes/confirm` 是這個系統唯一的寫入路徑。它寫的是照護記錄的稽核軌跡——
那是「誰在什麼時候對哪位病患記了什麼」的憑據。

原本的實作是 `open("a")` 加**兩次獨立的 `write`**、沒有 `flush`、沒有 `fsync`、
**完全沒有任何鎖**，而 handler 跑在 threadpool 的多個 worker thread 上。
更根本的是：它**完全不驗證那份草稿是不是這個系統產生的**。

## 決策

**「這份稽核軌跡值得信任」是一個命題，需要同時回答三件事。** 只做其中兩件，
會得到兩個各自不完整的機制：

| 問題 | 沒做的話會怎樣 | 機制 |
|---|---|---|
| **進來時是真的嗎** | 防竄改鏈會忠實地保護一筆一開始就是假的紀錄 | 草稿 HMAC 簽章 |
| **進去後沒被改嗎** | 有人改了紀錄，而你永遠不會知道 | hash chain |
| **併發下不會遺失嗎** | 紀錄靜靜地少了幾筆，或整行交錯壞掉 | 鎖 / 交易 |

第一點特別容易被漏掉，因為它看起來像認證的責任。**它不是**：
Phase 1 的 API key 回答的是「是誰打進來的」，而 `confirm` 收的是一份完整的
`CareNoteDraft`——一個通過認證的呼叫者仍然可以送出從來沒有經過 `propose` 的內容，
包括自己編的 `proposed_at`。

### 1. 草稿簽章用 HMAC，不用伺服器端暫存

`propose` 回傳草稿時附一個涵蓋**全部欄位**的 HMAC 簽章，`confirm` 驗簽後才寫。
無狀態——不需要暫存過期、清理、多實例共享。

漏簽任何一個欄位，那個欄位就可以被竄改：只簽 `patient_id` 的話，攻擊者可以把
`note_text` 換成任意內容再拿原簽章送出。測試對三個欄位各驗一次。

**沒設定金鑰時用 process 啟動時產生的隨機金鑰**。仍然擋得住偽造，只是重啟後先前
發出的草稿會失效——草稿本來就是短命的（使用者按下確認之前的那幾秒）。
維持了「少一個環境變數也能跑」。多實例部署時**必須**設共用金鑰，否則 A 實例發的
草稿到 B 實例會驗不過；這一點寫在 `.env.example` 與 README。

驗簽失敗回 **400 而不是 500**：那是 client 送了無效的東西，不是伺服器壞掉。

### 2. hash chain 放在紀錄模型層，不是資料庫層

每一列帶前一列的雜湊。改動任何一列都會讓它之後的所有列對不上。

**關鍵決定是放在哪一層**。如果鏈是靠 Postgres 的觸發器或約束實作的，
「無 `DATABASE_URL` 就退回檔案模式」這條降級路徑會**同時退掉防竄改**——
而那個降級是刻意保留的產品特性（demo 要能跑），不該是安全破口。
放在模型層則兩個後端拿到完全一樣的保證。

驗證程式把三種問題分開回報，因為它們代表不同的事：`row_hash` 對不上 =
這一列被改過；`prev_hash` 接不起來 = 前面有列被刪除、插入或重排；
`sequence` 不連續 = 同上但更直接。

**這個機制的極限（誠實記錄）**：它抓不出「有寫入權限的人重算了整條鏈」。
要防這個需要把鏈尾定期送到這個系統改不到的地方（外部時間戳、另一個帳號的儲存體），
超出這個 Phase 的範圍。**這個限制寫成了一個會通過的測試**
（`test_recomputing_the_whole_chain_is_not_detected`），讓「我們知道這件事」變成
可執行的紀錄，而不是只寫在文件裡的一句話。

### 3. 併發：Postgres 用 advisory lock，不是 `SELECT ... FOR UPDATE`

**這是實測踩到的 bug，不是理論考量。** 原本寫的是
`SELECT ... ORDER BY sequence DESC LIMIT 1 FOR UPDATE`，看起來很合理，
但它**只鎖住已經存在的那一列**，擋不住「另一個交易在它後面插入新列」：

- 兩個併發的 append 各自鎖住同一個鏈尾
- 先完成的插入 `sequence=N+1`
- 後完成的醒來時手上還是舊的鏈尾，也插 `N+1` → 主鍵衝突
- 表是空的時候更徹底：沒有列可鎖，所有交易一起衝 `sequence=0`

真的跑起來才會發現：`UniqueViolation: Key (sequence)=(1) already exists`。

改用 `pg_advisory_xact_lock`——鎖的是「append 這個動作」而不是某一列。
代價是所有 append 完全序列化；對稽核軌跡這種低頻寫入完全可以接受，
而且**鏈本來就是線性的**，序列化不是限制，是它的本質。

JSONL 模式用 `threading.Lock` + 單次原子寫入 + `fsync`。
**誠實記錄的限制**：鎖是 process 內的，多 process（`uvicorn --workers N`、
或多容器共用 volume）仍然不安全。那正是 Postgres 模式存在的理由，不是拿檔案鎖硬撐——
跨平台檔案鎖在 Windows 與 POSIX 語意不同，而且擋不住 NFS 之類的情況。

### 4. 資料庫是可選的，而且「設錯」要炸不要默默降級

無 `DATABASE_URL` → JSONL；有 → Postgres。`/api/health` 回報 `audit_backend`。

但**設定了 URL 卻沒裝 postgres extra 時刻意讓它炸掉**，不默默退回檔案模式：
那會讓人以為紀錄進了資料庫，其實在檔案裡。**稽核軌跡的位置不能靠猜。**

### 5. migration 用版本化 SQL，不用 alembic

一張表、一次 migration。為此引進整套 migration 框架講不出領域理由（ADR 0004 的標準）。
之後 schema 真的開始演化時再換。

### 6. FHIR 資料不進資料庫

資料庫裡只有稽核軌跡與預算計數。「LLM 物理上拿不到資料庫、每個臨床事實都經過
確定性工具」是這個專案的核心賣點，把 FHIR 塞進 DB 會把那條線弄糊（ADR 0001）。

### 7. 稽核紀錄補上 actor 與 request_id

原本的 `ConfirmedCareNote` 只有 4 個欄位，沒有 id、沒有 actor、沒有 request_id——
事後看不出「這筆是誰、透過哪一次請求寫的」。**稽核軌跡的價值一半在這裡。**

## 代價（實測）

- **image 大小 +27 MB（500 → 527 MB，+5.4%）**，來自 `psycopg[binary]`
- Postgres 模式的每次 append 多一次 advisory lock 的往返

## 已知限制

- 整條鏈被重算偵測不到（見上，有對應的測試）
- JSONL 模式多 process 不安全（見上）
- 草稿簽章金鑰未設定時是 process 臨時金鑰，重啟後舊草稿失效
- 既有的舊 JSONL 稽核檔（Phase 4 之前的格式，沒有 hash chain）**不會自動遷移**。
  新格式從新檔案開始；舊檔案保留原樣，用舊格式讀。這是刻意的：把沒有鏈的舊紀錄
  塞進鏈裡，等於宣稱它們有從來不存在的保證。

## 後果

- 之後任何新的寫入路徑都要走 `AuditSink`，不要再開一條直接寫檔的捷徑。
- `AuditSink` 刻意沒有 update 與 delete——與 `FHIRStore` 沒有 write 方法是同一個作法：
  做不到的事應該是「根本沒有這個方法」，不是「被擋下來」。
