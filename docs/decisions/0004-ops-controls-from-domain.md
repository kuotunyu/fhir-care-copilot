# ADR 0004：營運層的控制項從領域推導，不從技術清單推導

- 狀態：Accepted
- 日期：2026-07-25
- 相關：[ADR 0001](0001-scope.md)（範圍與安全邊界）

## 背景

M0–M7 交付的是「能跑的服務」：FastAPI 7 端點、React 工作台、Docker、128 個測試。
它缺的是營運層——認證、限流、可觀測性、韌性、稽核持久化，一個都沒有。
`/api/chat` 是完全開放的，而它每次呼叫都花真錢。

補這一層有一個明顯的失敗模式：照著「生產級服務該有什麼」的清單一路加下去，
最後得到一個掛著 Postgres、Redis、OTel、Grafana 的展示應用，而每一項都講不出
為什麼這個服務需要它。那不是工程，那是堆技術；而且在一個用合成資料的專案上，
它經不起「為什麼要這個」這一問。

## 決策

**每一個控制項都必須能從這個服務的一個具體事實推導出來。講不出領域理由的就不做。**

三個事實，三組控制：

| 事實 | 推導出的控制 | Phase |
|---|---|---|
| `/api/chat` 每次呼叫都花真錢，而端點完全開放 | API key 認證、每 key 限流、每日預算上限 | 1 |
| 日誌與 trace 會經手病患資料 | 結構化日誌的 PII 遮蔽、trace redaction | 2 |
| 會寫照護記錄的稽核日誌 | 可信任的稽核軌跡 | 4 |

這條規則有一個推論：**沒有消費端的可觀測性等於沒做**。產出 metrics 卻沒人讀、
產出 trace 卻沒地方看，只是換個形式的堆技術。所以 Phase 2 一定要附上能看的東西。

## Phase 1 的具體選擇與理由

### 為什麼是 API key，不是 OAuth / SSO

這個服務的呼叫者是「少數幾個受信任的整合端」，不是「大量互不相識的終端使用者」。
API key 對這個場景是正確的複雜度。OAuth 會引入 authorization server、token 生命週期、
refresh 流程——全部都在解決這個服務沒有的問題。

### 為什麼限流是 in-process，不是 Redis

Dockerfile 的 `CMD` 沒有 `--workers`，這是單一 uvicorn process。多加一個外部元件
目前講不出理由。代價誠實記在 `ops/ratelimit.py` 的模組 docstring 裡：
**多實例部署時每個實例各有一份計數，限流會變成 N 倍。** 真的要水平擴展時再換共用儲存。

### 為什麼用 `threading.Lock` 而不是 asyncio 原語

7 個端點全部是同步 `def`，FastAPI 會把它們丟進 anyio threadpool 執行。
計數器是被多個 worker thread 碰的，不是被 event loop 碰的。

### 為什麼限流是每 key、預算是全域

這是兩個不同的問題，刻意分開：

- **限流 = 公平性**。一個呼叫者不該把服務吃光 → 每個 key 各自一個 bucket。
- **預算 = 帳號保護**。會被燒光的是同一個 API 帳號的額度，不是某一把 key 的額度
  → 全 process 累計。

### 為什麼超出預算回 429 而不是 500

預算用完是「已知的、預期內的」拒絕，不是伺服器壞了。回 500 會讓監控誤判成故障，
也讓呼叫端無從分辨「該等一等」與「該回報 bug」。回應帶 `error_code`
（`rate_limited` / `budget_exceeded`）讓兩種 429 可以區分。

### 為什麼 `estimate_cost_usd` 的 `KeyError` 不 catch

`config.py` 的既有註解寫著「成本不可信比程式炸還危險」。守門這一層如果把它
catch 掉當成 0 元，預算上限就變成裝飾品——正好是這份 ADR 要防的那種東西。
副作用是它現在會在**花錢之前**就炸，比原本在 agent loop 最後才炸更早。

### 為什麼用 `Depends` 而不是 middleware

只掛在會花錢/會寫入的端點上，`/api/health` 就天然免疫。健康檢查被認證或限流擋住的話，
監控會在服務還活著的時候誤報死亡。用 middleware 就得維護一份路徑白名單，
而且要跟 `StaticFiles` 的 mount 順序打架。

### 為什麼前端的 key 是 UI 輸入 + localStorage，不是 build-time env

build-time env 會把金鑰烤進公開的 JS bundle，任何人打開 devtools 都讀得到——
對一個以安全紀律為賣點的專案是自相矛盾的。localStorage 並沒有比較「安全」
（同源指令碼一樣讀得到），但它誠實：金鑰是這個瀏覽器的使用者自己提供的，
不是我們發佈出去的。

### 三種降級行為

沿用「provider 缺金鑰自動退回 mock」的哲學——**不要讓服務因為少一個環境變數就起不來**，
但要在 `/api/health` 誠實標明現在少了什麼保護：

| 情況 | 行為 |
|---|---|
| 沒設定任何 API key | 認證層等於關閉，一律當 `anonymous` 放行 |
| 有設定金鑰，但請求帶了錯的 | 401。呼叫者顯然想認證，默默降級只會讓人搞不清楚狀況 |
| `REQUIRE_AUTH=true` 但沒有任何金鑰 | **Fail closed**。這是設定矛盾，fail open 等於「以為有保護，其實沒有」 |

**限流與預算不管有沒有開認證都生效**——demo mode 一樣會花錢。

## 已知限制（誠實記錄）

- 預算計數在記憶體，重啟即歸零。`/api/health` 回報 `budget_counting_since`，
  讓看的人知道這個數字是從什麼時候開始算的。持久化留給 Phase 4。
- 限流是單實例的（見上）。
- 前端的 `localStorage` 金鑰對同源的 XSS 沒有防護力。這個服務沒有使用者產生的
  HTML 內容，但這不是一個可以永遠成立的假設。

## 後果

- 每一個控制項在 README 都要能用上表的語言解釋它為什麼存在。
- 之後每加一個東西，先問「是哪個領域事實要求的」。答不出來就不加。
- 效能代價要量出來（Phase 0 基線 → Phase 5 對照），不是加完就宣稱沒影響。
